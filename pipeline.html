The persona pipeline

In build mode, your main Claude Code session conducts. It writes the plan, hands each piece of work to a named agent, checks what comes back against the files on disk, and makes the one commit at the end. The pipeline is built from Claude Code's own agents, hooks and settings.

The stages of a build

  1. Specify. Write the spec. Gate 1: you approve it before any work starts.
  2. Plan. Pick the risk tier and the budget, and split the work into ordered tasks. Gate 2: you approve the plan on standard or larger work.
  3. Build. The engineering swarm builds one task at a time, test first.
  4. Review. Review swarms run in parallel, chosen by tier.
  5. Synthesize. One ordered list of what to do about every finding. None is dropped.
  6. Verify. A fresh agent gets only the diff, the spec and the rubric, and decides pass or fail itself. A third failure means the plan was wrong: re-plan, do not keep fixing.
  7. Gate 3. You look at the visual or runtime result. A screenshot proves the render happened, not that it is right.
  8. Ship, when the change deploys, after a deploy-readiness interview.
  9. Close. The only commit, a decision-log entry and the memory sync.

Agent files

Setup writes one file per persona into .claude/agents/. Each file names when to hand work to that agent, and gives it the fewest tools that do the job. Reviewers get Read, Grep, Glob and Bash. Builders add Edit and Write. No agent gets the Agent tool, and the dispatch gate blocks a worker that tries to dispatch anyway. Each file also sets a model, an effort level and a turn limit. The body carries the persona's mandate, its anchors (the named standards it works to), what it must never do, and the two sections below on reasoning and briefs. A lint script must pass on every file.

The session never dispatches a worker at its own tier. A brief may lower a worker's tier but never raise it above its agent file. A leg that fails moves one tier up before the plan is redone. Risk picks the tier; the number of files touched does not. If a dispatch names no tier at all, the dispatch gate asks you.

A wave plan before a swarm

Before the first agent that can write is sent out, the conductor writes a plan to .claude/waves/<date>-<slug>.md. It names the result the wave is for, takes a read-only inventory of what is really there, and lists the work items. Each item has a write folder no other item shares, its dependencies, its model and effort, and a done-check. The plan also states the budget as arithmetic and names where you will be asked to decide. If there is no plan newer than the session start, the dispatch gate asks.

The brief

Every agent starts from a brief with the same parts: the goal in one sentence, the seated persona, the files it may touch, what it must not touch, the done-check, its budget, its model and effort, and a short prior of three to five hits from memory and the fix log. A brief for an agent that can write must carry the check on a line of its own:

Done-check: npm test exits 0

The words on their own line are what count. In the live test on 2026-10-13, the first dispatch was refused because its done-check sat inside a sentence. The agent returns a summary of one to two thousand tokens with the result first, the evidence, the paths it changed, what it did not do and why, and the cause, falsifier and evidence for its main claim.

The dispatch log and the worker hooks

Every dispatch that is not blocked is appended to .claude/.dispatch-log.jsonl: the time, the session, the agent type, the model tier and effort, the persona, the write folders and a SHA-256 hash of the prompt. A failure to write the log never stops the dispatch.

When a worker starts, the SubagentStart hook hands it its lane, a summary of the brief contract and its own line from the log. When it stops, the SubagentStop hook looks for evidence in its last message: a quoted span, an Evidence: line, or a path that exists. With none, the worker is sent back once with the reason. This shows the report names something real. It does not show the done-check passed; the conductor still checks that.

Causal logic as a persona rail

Every persona, the conductor included, states each claim as a chain: the cause, the mechanism, the falsifier that would show it wrong, and the evidence it actually collected. A report missing a link is incomplete and says which link. The docs give an example for a QA lead:

Claim
The refund-cap test guards the cap.
Cause
The test sends an over-cap refund and expects a 422, so removing the cap check makes it fail.
Falsifier
A mutant that deletes the cap check leaves the test green.
Evidence
A mutation run on the cap check turns the test red, with the output pasted.

A persona with no named standard behind it is rejected by the lint script before it can be seated. The docs put it as: no anchor, no seat.

Review swarms

Each swarm is staffed by personas and proves its own check can fail before it is trusted.

  • Engineering builds. Each task's test must fail before the change and pass after it. A test that passes against nothing halts the run.
  • Code review simplifies without changing behavior. The suite must pass the same way before and after. A planted behavior change must make a test fail first.
  • Trust and safety checks harm, abuse, privacy, accessibility and fairness against GDPR, CCPA and WCAG 2.2 AA. A seeded line that logs personal data must be caught.
  • Security runs red and blue: red finds, blue hardens, and each finding closes only when its fix is verified.
  • Ship and upload runs a deploy-readiness interview. A seeded missing environment variable or staged secret must block the ship.

Each review lens returns a score from 0 to 1, a pass or fail, and evidence. The score is the share of its checklist it covered with evidence. It is not a pass mark: one blocker fails the lens whatever the score.

The engineering principles

These come from Anthropic's published engineering guidance and the Claude Code docs. Each is tied to the mechanism that carries it.

Workflows before agents

Use the simplest pattern that solves the task. One call with retrieval beats a chain, and a chain beats a swarm. A new agent, loop or index has to name the failure it removes.

Bounded loops

No loop runs without a check that ends it, a stop condition and a turn, time or attempt cap. Each pass reads real output, such as a test exit code or a diff, not its own claim. State goes to disk each pass so a restart resumes.

Retrieval

Fetch what a step needs when it needs it, and keep paths rather than file bodies. A corpus under about 200,000 tokens goes into context whole, with caching, and gets no index.

DAG waves

Write each wave as a dependency graph with separate write folders per node. Independent nodes start together. Use one agent for a lookup and three to five in parallel for research. Resume from the failed node, not from the start.

Graphs

Ask a code graph a structure question ("what calls this?") before reading files to answer it. The graph tools are optional; without one, setup falls back to search and read.

Context

Workers return short summaries with paths for detail. Each agent gets the minimum tools, with no two covering the same job. Notes live in files so they survive when context is trimmed.

Evaluation

Grade the end state, not the route taken. The verifier is a fresh agent told to refute the claim, given only the diff and the criteria. Show the command and its output rather than asserting a result.
