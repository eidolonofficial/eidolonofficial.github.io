On the build, or the workshop under the hill

The persona pipeline

How one session conducts a company of named agents, from a spec you approve to a single commit.

In build mode, your main Claude Code session conducts. It plans and hands each piece of work to a named agent. It checks each result against the files on disk, and it makes the one commit at the end. All of it runs on Claude Code's own agents, hooks and settings.

Chapter 1

The stages of a build

A build runs these stages in order:

  1. specify
  2. plan
  3. build
  4. review
  5. synthesize
  6. verify
  7. ship (only when the change deploys)
  8. close

You approve the spec before work starts. You approve the plan on standard or larger work. At the end, you approve the visual or runtime result.

The verifier is a fresh agent. It sees only the diff, the spec and the rubric. A third failed verify means that the plan was wrong. Then the conductor makes a new plan and does not fix the old one again. Only the close stage commits.

Chapter 2

Agent files

Setup writes one file per persona into .claude/agents/. Each file says when to use that agent. It gives the agent the fewest tools that do the job. Reviewers get Read, Grep, Glob and Bash. Builders also get Edit and Write. No agent gets the Agent tool. The dispatch gate blocks a worker that tries to dispatch anyway.

Still open

In the live test, a spawn depth of 1 did not remove the Agent tool from a worker. So the dispatch guard is the control that stops recursion. No test shows yet whether Claude Code itself refuses a spawn at depth 1. The guard blocks the call first.

Each file sets a model, an effort level and a turn limit. Each file also carries these parts:

  • the mandate of the persona
  • its anchors, the named standards it works to
  • for the house persona, its problem-solving method: the root-cause framework it tries first
  • what it must never do
  • the reasoning and brief sections below

Each file must pass a lint script.

The session never dispatches a worker at its own tier. A brief can lower the tier of a worker. It never raises the tier above the agent file. A failed leg moves one tier up before the conductor makes a new plan. Risk picks the tier, not the number of files. A dispatch that names no tier gets a question from the dispatch gate.

Chapter 4

A wave plan before a swarm

Before the first agent that can write goes out, the conductor writes .claude/waves/<date>-<slug>.md. The plan names the result that the wave is for. It records a read-only inventory of what is really there. Then it lists the work items. Each item has these parts:

  • its own write folder
  • its dependencies
  • its model and effort
  • a done-check

The plan states the budget as arithmetic. It names the points where you decide. With no plan newer than the session start, the dispatch gate asks.

Chapter 5

The brief

Every agent starts from a brief. Each brief has the same parts:

  • the goal in one sentence
  • the seated persona
  • the files it may touch, and what it must not touch
  • the done-check
  • its budget, and its model and effort
  • a short prior of three to five hits from memory and the fix log

A brief for an agent that can write must carry the check on a line of its own:

Done-check: npm test exits 0

The line has to stand alone. In the live test on 2026-10-13, the gate refused the first dispatch. Its done-check sat inside a sentence.

The agent returns one to two thousand tokens, in this order:

  1. the result
  2. the evidence
  3. the paths it changed
  4. what it did not do, and why
  5. the cause, falsifier and evidence for its main claim
Chapter 6

The dispatch log and the worker hooks

The dispatch gate appends every dispatch that it does not block to .claude/.dispatch-log.jsonl. Each line holds these fields:

  • the time and the session
  • the agent type, tier and effort
  • the persona and the write folders
  • a SHA-256 hash of the prompt

A log failure never stops the dispatch.

When a worker starts, the SubagentStart hook hands it its lane. It also hands over a summary of the brief contract and the line of the worker from the log. When the worker stops, the SubagentStop hook looks for evidence in its last message. Evidence is a quoted span, an Evidence: line or a path that exists. With no evidence, the hook sends the worker back once with the reason.

What this does not do

The stop check shows that the report names something real. It does not show that the done-check passed. The conductor still checks that.

Chapter 7

Causal logic as a persona rail

Every persona states each claim as a chain. The conductor does too. The chain has four links:

  • the cause
  • the mechanism
  • the falsifier that would show it wrong
  • the evidence it actually collected

A report that lacks a link is incomplete. The report says which link it lacks. The docs give an example for a QA lead:

Claim
The refund-cap test guards the cap.
Cause
The test sends an over-cap refund and expects a 422. If you delete the cap check, the test fails.
Falsifier
A mutant that deletes the cap check leaves the test green.
Evidence
A mutation run on the cap check turns the test red, with the output pasted.

A persona with no named standard behind it fails the lint. Eidolon never seats it. The docs call this rule "no anchor, no seat."

Chapter 8

Review swarms

Personas staff each swarm. Each swarm must show that its own check can fail. Only then does its pass count.

Engineering
Builds. Each task's test must fail before the change and pass after it. A test that passes against nothing halts the run.
Code review
Simplifies and keeps the behavior the same. The suite passes the same way before and after. A planted behavior change must make a test fail first.
Trust and safety
Checks harm and abuse. It also checks privacy, accessibility and fairness. The standards are GDPR, CCPA and WCAG 2.2 AA. The swarm must catch a seeded line that logs personal data.
Security
Red finds and blue hardens. Each issue closes only when a check verifies its fix.
Ship and upload
Runs a deploy-readiness interview. A seeded staged secret must block the ship. So must a seeded environment variable that is absent.

Each review lens returns three things: a score from 0 to 1, a pass or fail, and evidence. The score is the share of its checklist that has evidence. It is not a pass mark. One blocker fails the lens whatever the score.

Chapter 9

The engineering principles

These principles come from the published guidance of Anthropic for engineers, and from the Claude Code docs.

Workflows before agents

Use the simplest pattern that solves the task. One call with retrieval beats a chain. A chain beats a swarm. A new agent, loop or index has to name the failure it removes.

Bounded loops

No loop runs without a check that ends it and a stop condition. It also needs a cap on turns, time or tries. Each pass reads real output, such as a test exit code or a diff. It does not read its own claim. State goes to disk each pass, so a restart resumes.

Retrieval

Fetch what a step needs when it needs it. Keep paths, not file bodies. A corpus under about 200,000 tokens goes into context whole with a prompt cache. It gets no index.

DAG waves

Write each wave as a dependency graph. Each node gets its own write folders. Independent nodes start together. Use one agent for a lookup. Use three to five agents in parallel for research. Resume from the failed node, not from the start.

Graphs

Ask a code graph a structure question ("what calls this?") before you read files to answer it. The graph tools are optional. Without one, setup falls back to search and read.

Context

Workers return short summaries with paths for detail. Each agent gets the minimum tools. No two tools do the same job. Notes live in files, so they survive a trim of the context.

Evaluation

Grade the end state, not the route. The verifier is a fresh agent. Its task is to refute the claim, and it gets only the diff and the criteria. Show the command and its output, not a bare claim of a result.
