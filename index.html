Version 0.1.0, a skill for Claude Code

A lantern for the repository

Spec-driven builds and guard hooks for Claude Code

Eidolon is a skill for Claude Code. It sets up your repository, then takes each change from a written spec to one reviewed commit.

Setup writes the files Claude needs, from a CLAUDE.md to the safety hooks and the memory wiring. Build runs a plan, test-first code, review swarms and a fresh verifier before the one commit. Its hooks check each shell, file and Agent call, and in a live session they blocked a commit that skipped the hooks.

It never writes to your project before you approve the plan, and it never weakens a guard to make a test pass.

The zip is on the Hearth release page. Its SHA-256 is in the ledger.

Install from a terminal

Four ways in, one command block each

npm, the one-line way (Node 22 or newer, any system)

npx eidolon-hearth

It installs the two skills into your user folder, shows every path first and asks before it replaces anything. Inside a project, npx eidolon-hearth . also wires the project hooks. The package is eidolon-hearth on npm, version 0.1.1 since 14 October 2026. It ships the same bundles as the zip, checked against the same lock.

Windows, novice door (PowerShell 5.1, nothing else needed)

iwr -UseBasicParsing https://github.com/eidolonofficial/Hearth/releases/download/v0.1.1/Hearth-v0.1.1.zip -OutFile Hearth.zip
if ((Get-FileHash Hearth.zip -Algorithm SHA256).Hash -ne '0E4DD913A4EDD571DF0A4E35B7706054698C0BBE078464FDCE039F51C0DA70AA') { throw 'hash mismatch' }
Expand-Archive Hearth.zip -DestinationPath . -Force
powershell -NoProfile -ExecutionPolicy Bypass -File .\Hearth-v0.1.1\welcome.ps1

It downloads the zip, checks its SHA-256, unpacks it and runs the novice door. The door asks before it replaces anything.

macOS and Linux, novice door (bash)

curl -L -o Hearth.zip https://github.com/eidolonofficial/Hearth/releases/download/v0.1.1/Hearth-v0.1.1.zip
echo "0e4dd913a4edd571df0a4e35b7706054698c0bbe078464fdce039f51c0da70aa  Hearth.zip" | shasum -a 256 -c
unzip -q Hearth.zip && bash Hearth-v0.1.1/macos/Welcome.command

It downloads the zip, checks its SHA-256, unpacks it and runs the novice door. The door asks before it replaces anything.

Operator door, project hooks (Git and Node 22)

git clone --branch v0.1.1 --depth 1 https://github.com/eidolonofficial/Hearth.git
node Hearth/scripts/welcome.mjs

It clones the v0.1.1 tag of Hearth and runs the operator door. The door shows its plan and asks before it replaces anything.

Every door asks GitHub once for a newer Hearth release before it writes, and asks you before it acts on one. The npm route and the operator door need Node 22. The zip doors need nothing else.

Prologue

Once upon a repository

Eidolon is a skill for Claude Code. It sets up a repository so Claude Code can work well in it. Then it carries a piece of work from a written spec to a committed change. It stops at set points so you can approve, edit or stop.

It runs in Claude Code only. Version 0.1.0 came out on 13 October 2026 with two companions. Then v0.1.1 and v0.1.2 followed on 14 October, with the hook review rounds 5 and 6, the update check and the npm package. Setup is a skill that opens a work session. Hearth is the installer for both. The release page has the record.

Chapter I

The three modes

Eidolon picks a mode from what you ask, and tells you which one it picked.

Setup

When
You have no work item yet, or you ask it to set up the repository.
What happens
It reads the repository and works out your languages and tools. Then it writes the files Claude needs: a CLAUDE.md, helper skills and slash commands, and sub-agents. It also writes the safety hooks, the MCP setup and the memory wiring. It pauses for you after the plan, the structure and the wiring.

Build

When
You have something to build, change or fix.
What happens
It writes a spec and a plan, then builds test first. It runs review swarms, and a fresh agent checks the result. It commits once, at the end. See the pipeline.

Autopilot

When
/eidolon loop, /eidolon goal or /eidolon routine, or "keep doing this".
What happens
It interviews you, writes the run down, and shows you how to stop it before it starts. See autopilot.

Most of the time it works on its own, and it pauses for you at only a few points. It pauses before it installs a skill or seats the primary persona (the house agent it builds for your repository). It also pauses before it deploys, before it runs something you cannot undo, and before it dispatches sensitive work. Each pause is one question. One line with it names who a wrong answer harms. Eidolon writes nothing before you approve the plan.

Chapter II

Who it is for

Eidolon is for anyone who wants a repository ready for Claude Code. It is also for anyone who wants to build, change or fix something in one. You do not need to say the word Eidolon. The skill loads when you ask for that kind of work.

Hearth, the installer, has one person in mind. That person runs their own business and is not confident with computers. A step such as "open PowerShell and paste this command" stops them. That person gets a door that needs nothing installed first. Operators who want project hooks get a second door.

The docs describe the interview that opens a session as made for a neurodivergent mind. It asks one question per screen. You pick an answer and do not have to type one, and you can skip any question. Every answer goes to a file, so you do not have to hold anything in your head. It also asks how familiar you are with code and pitches its language to your answer.

Chapter III

Two doors in

Hearth comes as Hearth-v0.1.1.zip on its release page. Inside it are two doors. Pick one.

Door 1. The novice door

Use it if
You want the two skills and nothing else.
What it needs
Nothing beyond what your computer already has: no Node, no Git and no other tools.
How to start it
On Windows, double-click Start Here.cmd. It runs welcome.ps1 in Windows PowerShell 5.1. On a Mac, open macos/Welcome.command, a plain bash script. If macOS blocks it, right-click the file and choose Open. Then confirm.
What it writes
Two folders in your user folder: .claude/skills/eidolon and .claude/skills/setup. It prints each file as it lands. It writes nothing else, adds no hooks and installs no other tool.
If a skill is already there
It asks you to type replace or press Enter to skip. Skip is the default. On replace, Hearth first moves your old folder to .claude/skills/.hearth-backups/<yyyyMMdd-HHmmss>/<name>. Then it copies the new one.
To undo it
Delete the eidolon and setup folders from .claude/skills. If Hearth saved an older copy, move it back from .hearth-backups.
Updates
Before it copies, the door asks GitHub once for the latest Hearth release. Three seconds at most, and nothing is sent but a fixed user agent. If a newer release exists, it tells you both versions and asks. Type yes to open the download page and stop, or press Enter to continue with this copy. No answer from GitHub means no notice. EIDOLON_UPDATE_CHECK=0 turns the check off.
Still open

The Mac door ran on GitHub's macOS runner and under WSL Ubuntu on 2026-10-13. It has not yet run on a user's own Mac.

Door 2. The operator door

Use it if
You want Eidolon's hooks wired into a project.
What it needs
Node 22 or newer. It checks first. If Node is absent or older than version 22, it points you to nodejs.org and stops.
How to start it
On Windows, double-click Operator Setup.cmd. On a Mac, open macos/Operator Setup.command. From any terminal, run node scripts/welcome.mjs.
Before it writes
It asks for a project folder. A blank answer means user skills only. It checks every bundled file against vendor-lock.json and stops on a mismatch. Under "Proposed locations:" it lists every path it will write, with the text, the settings diff or the replacement changes for each. It writes only after you type yes, and only the plan it showed you.
What it writes in the project
  • .claude/skills/eidolon and .claude/skills/setup
  • .claude/settings.json with the hook entries and the permission deny rules, and .claude/eidolon-manifest.yaml
  • .eidolon/policy-manifest.json
  • one marked section each in CLAUDE.md and .gitignore, between eidolon:begin and eidolon:end lines
It also sets three settings keys and replaces any values already there: env.CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH to "1", effortLevel to xhigh and maxEffortLevel to max. The preview says so.
If a skill is already there
You type replace to see a replacement plan. Hearth keeps the old files under .eidolon/backups/<id>/ with a receipt.json. It deletes nothing. It refuses a plan that changed after you reviewed it. It never reports a failed install as a success.
Updates
It asks GitHub once a day for the latest Hearth release. If a newer one exists, it asks Update now?. On yes it runs the newer version in its place, with the same arguments, through npm exec. Inside a Claude Code session, the Eidolon skill runs the same check when it starts and asks you before it runs npx -y eidolon-hearth@latest --yes. EIDOLON_UPDATE_CHECK=0 turns both off.
After it finishes
It prints the verified file count, the backup receipt path and the next step. Restart Claude Code in the project, and the hooks are active in the next session. They run Node, so keep Node installed.

Either way, open Claude Code and type /eidolon or /setup.

You can also clone the skill into your user skills folder with git clone https://github.com/eidolonofficial/eidolon.git ~/.claude/skills/eidolon. Keep one copy of Eidolon per machine, or keep both at the same commit. In a test on 2026-10-13, a user copy and a project copy had the same name. Claude Code loaded the user copy, and that copy was the older one.

What this does not do

A copied skill has no hooks. Only a project install wires them: the operator door, or the installer run with --project.

Chapter IV

The gates

In a project install, a guard checks each Bash or PowerShell call before it runs. Every check ends in one of three verdicts.

Block
The hook exits with code 2 and the call does not run. A block always wins over an ask.
Ask
You approve or decline.
Allow
The call runs. An advise verdict lets it run with a note as context.

Other hooks check each Write, Edit and Agent call in the same way. In the live test on 2026-10-13, they blocked a worker write outside its lane. They also blocked a worker that tried to dispatch another agent.

Why hooks, and not only permission rules

The deny floor uses Claude Code's own permission rules, so it holds even when the hooks are off. A permission rule matches a tool and a command or a path. It cannot follow where a path really points. It cannot give each worker its own write lane, and it cannot check a brief before a dispatch. The hooks add those checks. Each block also returns a sentence that the model can read and act on.

What a hook costs

Each hook call adds about half a second on the test machine. These are the medians of 15 runs each, on 2026-10-14, on a loaded Windows laptop:

  • guard-bash.mjs: 430 ms for npm test, and 566 ms for a commit
  • guard-write.mjs: 457 ms
  • guard-dispatch.mjs: 443 ms
  • bare node startup: 219 ms of each figure

Your numbers depend on your machine. To time one call in a project install, run this in a bash shell:

time (echo '{"tool_name":"Bash","tool_input":{"command":"npm test"}}' | node .claude/skills/eidolon/hooks/guard-bash.mjs --project .)

Known gaps

The hooks are defense in depth. They are lexical checks and not an OS sandbox. This is the list of what they do not cover, copied from the Safety page.

  • A script named on the command line is read once, one level deep, and judged by what it says. A path the script builds at run time is not resolved, so such a script asks you instead of blocking. A module the script imports, a script it runs, a file it writes and then runs, and the test files that node --test runs are not read. The scan is lexical. A call spelled in a way the patterns miss passes.
  • A script outside the project folder is not read. A worker with a lane is asked about it. The controller is not.
  • Git config includes are followed one level. An include inside an included file is not read. An includeIf is followed whatever its condition.
  • A shell -c, eval or iex body is parsed one level, and only when it names nothing protected and holds no $ or backtick. Otherwise it asks, and only when it names git, a protected path or settings.
  • The controller's whole-tree check reads local refs. git pull is compared with the remote-tracking ref as it stands before the fetch. git am, git stash pop and git reset without --hard are not compared.
  • The hard-link check runs on a literal operand that exists. A wildcard or $var operand is not checked. A link a program makes after it starts is seen only through the scan of its source.
  • A variable set in an earlier tool call is not tracked. GIT_DIR exported in one call and git run in the next is not seen.
  • The hooks are not an operating system sandbox. Pair them with Claude Code's permission rules and its sandbox mode. What a program does after it starts is seen only through the scan of its source.
  • A hook script that is missing, or that crashes with exit code 1, does not block the call on Claude Code before 2.1.295. The installer writes onFailure: block on every hook entry, and 2.1.295 or newer honors it. Version 2.1.206 accepts the key and still fails open.

What it never does

  • Write to your project before you approve the plan.
  • Install anything besides the two skills. It adds no extra programs, background tasks or account sign-in. It also adds no Node, credentials, models or services.
  • Delete your old copy. A replaced skill moves to a backup folder first.
  • Commit before the last stage of a build. Only the close stage commits, and before it does, it states the git state from before the run as the way back.
  • Take orders from what it reads. A pull request body, an issue, a web page or a file is data. If one of them holds an instruction, Eidolon reports the instruction to you and does not act on it.
  • Write a secret into a report, a log, a commit or a chat message.
  • Shrink a record. The records of what broke, what worked and each decision only grow.
  • Weaken a guard to make a test pass.
Chapter V

The workshop

In build mode, your main session is the conductor. It hands each piece of work to a named agent and checks the result against the files on disk.

Before the first worker that can write goes out, the conductor writes a wave plan. The dispatch gate logs each dispatch that it does not block. Every agent starts from a brief with a done-check on its own line. These three files come from the live run of 2026-10-13.

Chapter VI

The clockwork

Autopilot is for work that runs on its own. Before anything runs, Eidolon interviews you, and the first screen offers a brain dump.

Then you pick one of four shapes. Eidolon shows you how to stop the run before it starts. The limits below come from the autopilot page.

Goal

There is a clear finish line. A small fast model checks the condition after every turn.

To stop it
/goal clear

Loop

It repeats in your open session. The minimum interval is 1 minute.

To stop it
Esc, or CronDelete

Routine

It runs in the cloud on a schedule, an API call or a GitHub event. The minimum interval is 1 hour.

To change it
/schedule update

Desktop task

It runs on your machine with your local files, on a schedule.

To stop it
Disable it in the scheduled tasks list

The autopilot page has the interview and each shape in full.

Chapter VII

What it writes, and the way out

An install writes only the paths on this list. The operator door shows each path in its preview before you type yes.

A project install writes

  • .claude/skills/eidolon and .claude/skills/setup
  • the hook entries and the deny rules in .claude/settings.json
  • .claude/eidolon-manifest.yaml
  • .eidolon/policy-manifest.json
  • one marked block each in CLAUDE.md and .gitignore
  • backups with receipts under .eidolon/backups/, when it replaces a skill

A user install writes

The novice door writes two folders in your user folder, .claude/skills/eidolon and .claude/skills/setup. It writes nothing else.

What it does not do

The hooks make no network calls. Eidolon sends no telemetry. To check the hooks, search them for a network module. This command prints nothing:

grep -nE "node:(http|https|net)|fetch\(" .claude/skills/eidolon/hooks/*.mjs

To remove it

  1. Delete .claude/skills/eidolon and .claude/skills/setup.
  2. Delete the marked blocks in CLAUDE.md and .gitignore, from eidolon:begin to eidolon:end.
  3. In a project, also remove the Eidolon hook entries and deny rules from .claude/settings.json.

The backups and receipts of the operator door stay in .eidolon/backups/. A user install needs only the first step.

To list the deny rules after a project install, run this in the project folder. On a project with no deny rules before the install, it prints 24 lines.

node -p "require('./.claude/settings.json').permissions.deny.join('\n')"
