On safety, or the keeper of the gates

How the guards work

What the hooks block or ask you about, and the written list of what they cannot see.

Eidolon's hooks are defense in depth. They are lexical checks on Claude Code tool calls, plus a floor of permission deny rules. They are not an operating system sandbox, and what they cannot see is listed under known gaps.

Before the first chapter

Three verdicts

Every check ends in one of three verdicts:

Block
The hook exits with code 2 and the call does not run. Claude sees the reason.
Ask
You approve or decline. Several asks about one call become one question.
Advise
The call runs and a note rides along as context.
What this does not do

Only a project install wires the hooks: the operator door, or the installer run with --project. A skill copied by the novice door or by git clone has no hooks.

A block always wins over an ask.

Chapter 1

The deny floor

One edit to a settings file can silence every hook. So the floor has two layers. The first is a list of permission deny rules in .claude/settings.json. Claude Code's own permission parser reads them, so they hold even when someone turns the hooks off. They refuse a force push (--force or -f) and a git config of core.hooksPath. They also refuse filter-branch, filter-repo and any Write or Edit of .claude/settings.local.json. Each rule covers Bash and PowerShell alike. A project install adds Write and Edit denials for the installed skill, the policy manifest, the session state and the Eidolon manifest. The rules leave git push --force-with-lease alone.

The second layer is the hooks. A permission rule matches a tool and a command or path, never file content. "This write turns on disableAllHooks" is a fact about content, so a hook checks it.

Chapter 3

Write lanes

A worker that can write anywhere can undo the controller's gates. So each worker gets a lane in .claude/agent-scopes.json. The lane names the folders the worker may read and write. The hooks block a worker's Write, Edit or shell write outside its lane. They also block any worker write outside the project, but they allow scratch files in the system temp folder. A reviewer gets an empty write list. A worker with no entry has no lane. The controller is your main session, and it never has a lane.

Chapter 4

The dispatch gate

When the controller hands work to an agent, guard-dispatch.mjs checks the hand-off.

  • It asks you when the task names sensitive work. Sensitive work includes a deploy, a migration, personal data and payments. It also includes credentials, a deletion and a force push.
  • It blocks a worker that tries to dispatch another worker.
  • For a worker that can write, it asks when the brief has no line that starts with Done-check: (or Acceptance:) and a real check after it. It treats none, tbd and similar placeholders as no check.
  • For a worker that can write, it asks when .claude/waves/ holds no plan of at least 20 characters newer than the session start.
  • It asks when the dispatch names no model tier.
  • It logs every dispatch it does not block to .claude/.dispatch-log.jsonl.
Chapter 5

The commit rules

  • The hooks block --no-verify on a commit or a push. They also block its short form -n on a commit.
  • They block a force push. They pass --force-with-lease on its own.
  • They block a mirror push, a core.hooksPath override, filter-branch and filter-repo.
  • They block a commit message that says a screen or a run works but names no evidence.
  • A commit that stages an image, video or PDF with no evidence named asks first.
  • Commands that throw away uncommitted work, such as git reset --hard or git clean -f with no path, ask first.
  • The records in docs/fixes/, docs/insights/ and docs/decisions/ only grow. The hooks pass an append to a record. They block a write that overwrites or deletes one.
Chapter 6

What asks and what blocks

Besides the dispatch and commit cases above, these ask you:

  • A change the parser cannot place, such as a wildcard or unexpanded variable that can reach a protected file.
  • Code passed as a string to an interpreter, such as node -e, python -c or eval. The hooks ask when that code names git, a protected path, settings or hooks.
  • An archive that unpacks with no destination folder, or into the project root.
  • A command it cannot parse.
  • A write to a hook file by the controller. The hooks block a worker that does the same.

These are blocked:

  • A delete or a move of .git, a hook or the persona template. The same goes for the security policy, a record and a folder that holds one.
  • A shell command that changes a settings file or the installed skill.
  • A settings write that turns hooks off, or drops a hook entry or deny rule the install manages.
  • Writing through a file that has more than one hard link.
  • Spellings that once slipped past: 8.3 short names, alternate data streams, /c/ drive paths and symlinks.

These are the short versions. A call that matches neither full list in the README passes.

Chapter 7

Known gaps

These are the shapes the checks and the deny floor do not cover, as of v0.1.1. Review rounds 5 and 6 closed the earlier list. Scripts named on a command line are now read and judged. So are node -e and python -c bodies. Git aliases are expanded. Subshells are scoped. Encoded PowerShell commands are decoded. Archive escapes, hard links onto records and GIT_DIR prefixes block.

  • A script named on the command line is read once, one level deep, and judged by what it says. A path the script builds at run time is not resolved, so such a script asks you instead of blocking. A module the script imports, a script it runs, a file it writes and then runs, and the test files that node --test runs are not read. The scan is lexical. A call spelled in a way the patterns miss passes.
  • A script outside the project folder is not read. A worker with a lane is asked about it. The controller is not.
  • Git config includes are followed one level. An include inside an included file is not read. An includeIf is followed whatever its condition.
  • A shell -c, eval or iex body is parsed one level, and only when it names nothing protected and holds no $ or backtick. Otherwise it asks, and only when it names git, a protected path or settings.
  • The controller's whole-tree check reads local refs. git pull is compared with the remote-tracking ref as it stands before the fetch. git am, git stash pop and git reset without --hard are not compared.
  • The hard-link check runs on a literal operand that exists. A wildcard or $var operand is not checked. A link a program makes after it starts is seen only through the scan of its source.
  • A variable set in an earlier tool call is not tracked. GIT_DIR exported in one call and git run in the next is not seen.
  • The hooks are not an operating system sandbox. Pair them with Claude Code's permission rules and its sandbox mode. What a program does after it starts is seen only through the scan of its source.
  • A hook script that is missing, or that crashes with exit code 1, does not block the call on Claude Code before 2.1.295. The installer writes onFailure: block on every hook entry, and 2.1.295 or newer honors it. Version 2.1.206 accepts the key and still fails open.
Chapter 8

How the docs are kept true

The project treats hooks/README.md as output generated from the code. The script scripts/hooks-readme-check.mjs compares the two. It checks the wiring, the order of the checks and the hook rows. It also checks the project argument, the "What asks" section title and the absence of dashes.

Before v0.1.0, the hooks went through three review rounds and the installer through two, with the findings fixed test first. Rounds 5 and 6 followed for v0.1.1, both by execution, and round 6 fixed what round 5 had over-blocked. Each round replayed the previous round's payloads and 60 ordinary developer commands, so a fix that blocked normal work showed up. The release page has the counts.

The decision record names every round, gate and live test, and each open item with the check that settles it.

Colophon

Every claim on these pages traces to a document in the three repositories.

The pages are static HTML and one stylesheet. The pages with copy buttons carry one small first-party script for those buttons, with no external scripts and no tracking. Every version number on these pages comes from one file, versions.json, and the checker refuses a page that disagrees with it. The type is Fraunces, Instrument Sans and IBM Plex Mono, from Google Fonts. The drawings are inline SVG.
