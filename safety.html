How the guards work

Eidolon's hooks are defense in depth. They are lexical checks on Claude Code tool calls, plus a floor of permission deny rules. They are not an operating system sandbox, and what they cannot see is listed under known gaps.

Every check ends in one of three verdicts:

Block
The hook exits with code 2 and the call does not run. Claude sees the reason.
Ask
You approve or decline. Several asks about one call become one question.
Advise
The call runs and a note rides along as context.

A block always wins over an ask. Only a project install wires the hooks: the operator door, or the installer run with --project. A skill copied by the novice door or by git clone has no hooks.

The deny floor

One edit to a settings file could silence every hook, so the floor has two layers. The first is a list of permission deny rules in .claude/settings.json. Claude Code's own permission parser reads them, so they hold even when hooks are turned off. They refuse a force push (--force or -f), a git config of core.hooksPath, filter-branch, filter-repo, and any Write or Edit of .claude/settings.local.json, for Bash and PowerShell alike. A project install adds Write and Edit denials for the installed skill, the policy manifest, the session state and the Eidolon manifest. git push --force-with-lease is left alone.

The second layer is the hooks. A permission rule matches a tool and a command or path, never file content. "This write turns on disableAllHooks" is a fact about content, so a hook checks it.

Write lanes

A worker that can write anywhere could undo the controller's gates. So each worker gets a lane in .claude/agent-scopes.json, naming the folders it may read and write. A worker's Write, Edit or shell write outside its lane is blocked, as is any worker write outside the project; scratch files in the system temp folder are allowed. A reviewer gets an empty write list. A worker with no entry has no lane, and the controller, your main session, never has one.

The dispatch gate

When the controller hands work to an agent, guard-dispatch.mjs checks the hand-off.

  • It asks you when the task names sensitive work, such as a deploy, a migration, personal data, payments, credentials, deleting or a force push.
  • It blocks a worker that tries to dispatch another worker.
  • For a worker that can write, it asks when the brief has no line starting Done-check: (or Acceptance:) with a real check after it. none, tbd and similar placeholders count as missing.
  • For a worker that can write, it asks when .claude/waves/ holds no plan of at least 20 characters newer than the session start.
  • It asks when the dispatch names no model tier.
  • It logs every dispatch it does not block to .claude/.dispatch-log.jsonl.

The commit rules

  • --no-verify, or -n on a commit, is blocked on commit and push.
  • A force push is blocked. --force-with-lease on its own passes.
  • A mirror push, a core.hooksPath override, filter-branch and filter-repo are blocked.
  • A commit message saying a screen or a run works, with no evidence named, is blocked.
  • A commit that stages an image, video or PDF with no evidence named asks first.
  • Commands that throw away uncommitted work, such as git reset --hard or git clean -f with no path, ask first.
  • The records in docs/fixes/, docs/insights/ and docs/decisions/ only grow. Appending passes; overwriting or deleting one is blocked.

What asks and what blocks, in short

Besides the dispatch and commit cases above, these ask you:

  • A change the parser cannot place, such as a wildcard or unexpanded variable that could reach a protected file.
  • Code passed as a string to an interpreter (node -e, python -c, eval and the like) that names git, a protected path, settings or hooks.
  • Unpacking an archive with no destination folder, or into the project root.
  • A command it cannot parse.
  • The controller writing a hook file. A worker doing the same is blocked.

These are blocked:

  • Deleting or moving .git, a hook, the persona template, the security policy or a record, or a folder that holds one.
  • A shell command that changes a settings file or the installed skill.
  • A settings write that turns hooks off, or drops a hook entry or deny rule the install manages.
  • Writing through a file that has more than one hard link.
  • Spellings that once slipped past: 8.3 short names, alternate data streams, /c/ drive paths and symlinks.

These are the short versions. A call that matches neither full list in the README passes.

Known gaps

The hooks README puts it plainly: a guard that claims more than it does is worse than none. These are the shapes the checks and the deny floor do not cover.

  • A script file a worker runs (node build.js, sh run.sh) does whatever it does. The guards see only its command line.
  • A wildcard or $var path does not trigger the lane check.
  • Code inside node -e, python -c and other interpreters is never parsed. A node -e call that deletes docs with rmSync passes.
  • Git aliases defined in .git/config are not visible.
  • A subshell is judged command by command, not as a unit.
  • PowerShell -EncodedCommand bodies are not decoded; the command asks.
  • The controller may still run git checkout, switch, merge, pull, rebase and other whole-tree commands. Only those that discard uncommitted work ask.
  • A hard link made by a script, or behind a wildcard, is not seen. Linking a whole parent folder with cp -al or rsync --link-dest is not judged as linking the records inside it.
  • GIT_DIR or GIT_CONFIG_COUNT set in a bash prefix or export is not blocked. The PowerShell forms are, but only when git runs in the same command.
  • A PowerShell call target held in a variable (& $cmd) is not resolved.
  • An archive unpacked into an unprotected folder can hold entries that climb out of it.
  • A project inside the temp folder gives its workers no scratch space.
  • The controller's own writes outside the project are not judged, except to settings files.
  • The README lists a worker's agent type as unverified until a live debug run. In the live run of 2026-10-13, the worker's inputs did carry it.
  • The hooks are not an operating system sandbox.
  • A hook script that is missing, or crashes with exit code 1, does not block the call. Claude Code shows the error and carries on. Turning that into a block needs Claude Code 2.1.295 or newer.

How the docs are kept true

hooks/README.md is treated as generated from the code. scripts/hooks-readme-check.mjs compares the two: the wiring, the order of the checks, the hook rows, the project argument, the "What asks" heading and the absence of dashes. A hook change and its README change land in the same commit, and the check is never silenced.

Before v0.1.0, the hooks went through three review rounds and the installer through two, with the findings fixed test first. Each round replayed the previous round's payloads and 60 ordinary developer commands, so a fix that blocked normal work showed up. The release page has the counts.

The decision record names every round, gate and live test, and each open item with the check that would settle it.
