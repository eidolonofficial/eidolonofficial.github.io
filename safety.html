How the guards work

Eidolon's hooks are defense in depth. They are lexical checks on Claude Code tool calls, plus a floor of permission deny rules. They are not an operating system sandbox, and the list of what they cannot see is further down this page.

Every check ends in one of three verdicts:

  • Block. The hook exits with code 2 and the call does not run. Claude sees the reason.
  • Ask. You approve or decline. When several checks ask about one call, you get one question.
  • Advise. The call runs and a note rides along as context.

A block always wins over an ask. The hooks are wired only by a project install: the operator door, or the installer run with --project. A skill copied by the novice door or by git clone has no hooks.

The deny floor

One edit to a settings file could silence every hook. So the floor has two layers.

The first layer is a list of permission deny rules in .claude/settings.json. Claude Code's own permission parser reads them, so they still hold when hooks are turned off. They refuse a force push (--force or -f), any git config of core.hooksPath, git filter-branch, git filter-repo, and any Write or Edit of .claude/settings.local.json. Each Bash rule has a PowerShell twin. A project install adds Write and Edit denials for the installed skill, the policy manifest, the session state and the Eidolon manifest. The rules leave git push --force-with-lease alone.

The second layer is the hooks themselves. A permission rule matches a tool and a command or path, never file content. "This write turns on disableAllHooks" is a fact about content, so a hook checks it.

Write lanes

A worker that can write anywhere could undo the controller's gates. So each worker gets a lane in .claude/agent-scopes.json: the folders it may read and the folders it may write. A worker's Write, Edit or shell write outside its lane is blocked, and so is any worker write outside the project. Scratch files in the system temp folder are allowed. A reviewer gets an empty write list. A worker with no entry in the file has no lane. The controller, your main session, is never held to a lane.

In a live run on 2026-10-13, a builder agent with the lane src/** wrote src/hello.txt. Its attempts to write into docs/, once through Write and once through a shell redirect, were both blocked by the lane guard.

The dispatch gate

When the controller hands work to an agent, guard-dispatch.mjs checks the hand-off first.

  • It asks you when the task text names sensitive work, with words such as security, deploy, release, production, migration, personal data, payment, credential, secret, delete or force push.
  • It blocks a worker that tries to dispatch another worker.
  • For a worker that can write, it asks when the brief has no line that starts with Done-check: (or Acceptance:) followed by a real check. A placeholder such as none or tbd counts as missing.
  • For a worker that can write, it asks when no wave plan in .claude/waves/, at least 20 characters long, is newer than the start of the session.
  • It asks when the dispatch names no model tier.
  • It writes one line per dispatch to .claude/.dispatch-log.jsonl.

The commit rules

  • Skipping hooks with --no-verify, or -n on a commit, is blocked on commit and push.
  • A force push is blocked. --force-with-lease on its own passes.
  • A mirror push, a core.hooksPath override, and filter-branch or filter-repo are blocked.
  • A commit message that says a screen or a run works, with no evidence named, is blocked.
  • A commit that stages an image, video or PDF with no evidence named in the message asks first.
  • Commands that throw away uncommitted work, such as git reset --hard or git clean -f with no path, ask first.
  • The records in docs/fixes/, docs/insights/ and docs/decisions/ only grow. Appending passes. Overwriting or deleting one is blocked.

What asks and what blocks, in short

These ask you

  • A change the parser cannot place, such as a wildcard or an unexpanded variable that could reach a protected file.
  • Code passed as a string to an interpreter (node -e, python -c, eval and the like) that mentions git, a protected path, settings or hooks.
  • Unpacking an archive with no destination folder, or into the project root.
  • A command it cannot parse at all.
  • The controller writing a hook file. A worker doing the same is blocked.
  • The dispatch cases above.

These are blocked

  • Changing or deleting .git, a settings file, the installed skill, a hook, the persona template, the security policy or a record, by any verb the parser models.
  • Deleting or moving a folder that holds one of those.
  • Turning hooks off in settings, or dropping a hook entry or deny rule the install manages.
  • Writing through a file that has more than one hard link.
  • Spellings that once slipped past: short 8.3 names, alternate data streams, /c/ drive paths and symlinks.

These lists are short versions. The full lists are in the hooks README, and a call that matches neither of them there passes.

Known gaps

A guard that claims more than it does is worse than none. These are the shapes the checks and the deny floor do not cover, as listed in the hooks README.

  • A script file a worker runs (node build.js, sh run.sh) does whatever it does. The guards see only its command line.
  • A wildcard or $var path does not trigger the lane check.
  • Code inside node -e, python -c and other interpreters is never parsed. A node -e call that deletes docs through rmSync passes.
  • Git aliases defined in .git/config are not visible.
  • A subshell is judged command by command, not as a unit.
  • PowerShell -EncodedCommand bodies are not decoded; the command asks.
  • The controller may still run git checkout, switch, merge, pull, rebase and similar whole-tree commands. Only the ones that discard uncommitted work ask.
  • A hard link made by a script, or one hidden behind a wildcard, is not seen. Linking a whole parent folder with cp -al or rsync --link-dest is not judged as linking the records inside it.
  • GIT_DIR or GIT_CONFIG_COUNT set in a bash prefix or export is not blocked. The PowerShell forms are, but only when git runs in the same command.
  • A PowerShell call target held in a variable (& $cmd) is not resolved.
  • An archive unpacked into an unprotected folder can still hold entries that climb out of it.
  • A project inside the temp folder gives its workers no scratch space.
  • The controller's own writes outside the project are not judged, except settings files.
  • The README lists the arrival of a worker's agent type as unverified until a live debug run. In the live run of 2026-10-13, the worker's inputs did carry it.
  • The hooks are not an operating system sandbox.
  • A hook script that is missing, or that crashes with exit code 1, does not block the call. Claude Code shows the error and carries on. Making that a block needs Claude Code 2.1.295 or newer.

How the docs are kept true

hooks/README.md is treated as if it were generated from the code. A script, scripts/hooks-readme-check.mjs, compares the README with the code: the wiring, the order of the checks, the hook rows, the project argument, the "What asks" heading and the absence of dashes. When a hook changes, the README changes in the same commit. The check is never silenced.

Before v0.1.0, the hooks went through three review rounds and the installer through two, each against a named commit. Each round replayed the previous round's payloads and 60 ordinary developer commands, so a fix that blocked normal work showed up as a false positive and was fixed in the next round. The hook and installer findings were fixed test first. The release page has the counts.

The decision record docs/decisions/2026-10-13-archive-branches-and-v010-re-cut.md names every round, every gate and every live test, and what is still unverified with the check that would settle it. Like the other records, it is only appended to.
